# 노션식 데이터베이스 · 공개 API — 가능성 검토

작성일: 2026-09-14 / 선행: `2026-09-14_obsidian-style-document-features.md`

결론 먼저.

- **공개 API** — 가능하다. 기반의 대부분이 이미 있고, 빠진 건 네 가지뿐이다. **먼저 하는 게 맞다.**
- **노션 DB** — 가능하지만 크다. 절반은 이미 있는데, 그 "이미 있는 절반"이 오히려 가장 큰 위험이다.

## 1. 노션 DB

### 1-1. 이미 있는 것 — 생각보다 많다

| 노션 개념 | OrbiTail 현황 |
|---|---|
| 타입 있는 속성 | **Issue 가 사실상 DB 한 벌이다** — 상태·우선순위·담당자(다중)·라벨(다중선택)·스프린트·카테고리·상위·시작/마감일·예상 포인트 |
| 뷰 | 테이블 · 보드 · 캘린더 · 타임라인 · 그래프 · 스프린트 · 리포트 |
| 필터·정렬 | 이슈 뷰에 있음 |
| **인라인 데이터베이스** | **`issueViewEmbed` — 문서 안에 뷰를 끼워 넣는 것이 이미 동작한다** |
| 다중 선택 | `DocumentLabel` / `Label` |
| 행이 곧 페이지 | 이슈에 `description_html`, 문서는 그 자체가 페이지 |
| 속성 자유 입력 | `Document.properties`(2026-09-14 추가) — 단 **타입이 없다** |

### 1-2. 진짜 빠진 것 — 하나뿐이다

**사용자가 스키마를 정의하는 것.** 지금 스키마는 전부 코드에 박혀 있다.

> 혼동 주의: `Issue.is_field` 는 사용자 정의 필드가 **아니다**. "상태가 없는 묶음용 상위 이슈"
> 플래그다(`models.py:89`). 이름 때문에 커스텀 필드가 이미 있는 것처럼 읽힌다.

### 1-3. 설계 방향

동적 테이블 생성(데이터베이스마다 실제 테이블)은 **하지 않는다** — 마이그레이션·백업·권한이 전부 깨진다.

```
DocumentDatabase   스키마 정의 (이름, 스페이스, 속성 목록)
  properties: [{key, type, options?, ...}]   # select/multi_select/date/number/person/checkbox/url/relation
DatabaseView       뷰 (종류, 필터, 정렬, 그룹, 보이는 속성)
행                 Document (properties JSONB 를 스키마로 검증)
```

Postgres JSONB + GIN 인덱스면 필터·정렬이 선다. `Document.properties` 가 이미 그 자리를 잡고 있다.

### 1-4. 난이도 계단

| 단계 | 내용 | 비용 | 비고 |
|---|---|---|---|
| T1 | 스키마 정의 + 타입 있는 속성 + 테이블 뷰 + 필터·정렬 | 중 | `properties` 위에 타입을 씌우는 일. 기반은 놓여 있다 |
| T2 | 보드 · 갤러리 · 캘린더 뷰 + 그룹화 | 중 | **기존 이슈 뷰 재사용을 기대하지 말 것** — 아래 참조 |
| T3 | 릴레이션 + 롤업 | 큼 | `DocumentLink` 가 뼈대가 되지만 "어느 속성으로 이어졌는지"를 담을 컬럼이 필요 |
| T4 | 수식(formula) | 매우 큼 | 표현식 언어 + 평가기 + 순환 참조 탐지. **권장하지 않음** |

**T2 의 재사용 경고는 추측이 아니다.** 이번에 문서 그래프를 만들며 `GraphView.tsx`(1631줄)를
일반화하려다 포기했다 — 이슈 고유 개념이 너무 얽혀 있었다. 테이블/보드/캘린더 뷰도 같은 상태일
가능성이 높으니, 착수 전에 한 곳(예: BoardView)만 열어 결합도를 먼저 재 볼 것.

### 1-5. 가장 큰 위험 — 평행한 DB 두 개

문서 DB 를 만들면 **이슈와 문서 DB 라는 두 개의 데이터베이스 개념**이 생긴다.
라벨 vs 인라인 태그에서 피했던 "분류축이 갈라지는" 함정과 같은 모양인데, 규모가 훨씬 크다.

착수 전에 이것부터 정해야 한다:

- **(가) 흡수** — 이슈를 "내장 스키마를 가진 DB 한 종류"로 다시 정의. 개념이 하나로 남아 옳지만,
  스프린트·번다운·상태 워크플로·활동 로그를 전부 새 구조 위에 얹어야 하는 대공사다.
- **(나) 병행** — 이슈는 그대로 두고 문서 DB 를 따로. 싸지만, 사용자에게 "표를 만들려면 둘 중 뭘 쓰나"가 평생 남는다.

지금 판단으로는 **(나)로 시작하되 (가)로 갈 수 있는 모양을 지키는 것** — 즉 DB 스키마·뷰 모델을
문서 전용으로 만들지 말고 처음부터 "대상 종류"를 갖게 설계하는 것 — 이 현실적이다.

## 2. 공개 API

### 2-1. 이미 있는 것 — 80% 쯤

| 필요한 것 | 현황 |
|---|---|
| REST 전면 | DRF 로 전부 구현되어 있음 |
| 스키마 문서 | **`drf-spectacular` 가동 중** — `/api/schema/`, `/api/docs/`(Swagger) |
| 인증 | JWT(SimpleJWT) |
| 스로틀링 | 설정됨 — anon 60/분, user 1200/분, auth 10/분 |
| 비동기 작업 | Celery + Redis 가동 중 → 웹훅 재시도 큐로 쓸 수 있다 |
| **문서 읽기/쓰기 형식** | **마크다운 양방향 변환이 방금 생겼다**(`apps/documents/markdown.py`) |

### 2-2. 빠진 것 — 넷

1. **기계용 자격증명** ★ 가장 먼저
   JWT 는 사람 세션용이다(기본 60분 만료, refresh 로 연장). 통합 토큰이 필요하다 —
   워크스페이스 귀속, 스코프(읽기/쓰기·대상), 폐기, 마지막 사용 시각, 노출은 발급 시 1회.

2. **공개 계약의 분리**
   지금 `/api/schema/` 는 내부 엔드포인트를 전부 드러낸다. 그대로 공개하면 **내부 리팩터가 곧 외부 파괴**다.
   공개용 하위 집합 + 버전(`/api/v1/`)을 따로 세워야 한다.

3. **웹훅**
   아웃바운드 이벤트(이슈 생성·문서 변경) + 서명(HMAC) + 재시도 + 실패 보관.
   Celery 가 이미 있어 중간 난이도.

4. **스코프별 스로틀**
   지금은 사용자 단위 하나뿐. 토큰별·스코프별 제한이 필요하다.

### 2-3. 블록 API 는 만들지 말 것을 권합니다

노션은 블록 트리를 그대로 노출한다(`/blocks/{id}/children`). 우리는 **HTML + Yjs** 다.
블록 API 를 흉내 내면 두 가지가 깨진다.

- **동시 편집과 충돌한다.** 누군가 편집 중인 문서에 외부에서 REST 로 쓰면 Yjs 상태와 어긋나
  덮어쓰기가 난다. 이건 가정이 아니라 현재 구조상 확실한 문제다.
- 블록 id 가 안정적이지 않다. Yjs 협업 중 블록 경계가 바뀐다.

**맞는 모양**: 문서 단위 `text/markdown` in/out. 마크다운 변환이 이미 있으니 거의 공짜로 나온다.
다만 **"실시간 편집 중인 문서에 외부 쓰기가 들어오면 어떻게 할 것인가"는 반드시 먼저 정해야 한다** —
거절할지(409), 편집자가 없을 때만 받을지, Yjs 로 적용할지. 이건 API 를 내기 전에 답이 있어야 한다.

### 2-4. 순서

| 순서 | 내용 | 이유 |
|---|---|---|
| 1 | 통합 토큰(스코프·폐기·감사) | 나머지 전부의 전제 |
| 2 | 공개 v1 표면 확정 + 문서 | 내부/외부 경계를 먼저 그어야 뒤가 안 흔들린다 |
| 3 | 문서 마크다운 in/out + 동시 편집 충돌 정책 | 변환기가 이미 있어 싸다. 단 정책 합의가 선행 |
| 4 | 웹훅 | 위 셋이 있어야 쓸모가 생긴다 |

## 3. 종합 권고

**API 를 먼저, DB 를 나중에.**

- API 는 **DB 없이도 쓸모가 완결된다**(이슈·문서만으로 자동화가 성립). 비용도 훨씬 작다.
- DB 는 개념 통합 결정(1-5)이 선행돼야 하고, 그 결정이 API 계약에도 영향을 준다.
- 순서를 뒤집으면 DB 가 들어올 때 v1 계약을 깨게 된다. 먼저 낸다면 **v1 을 이슈·문서로 한정**하고
  DB 는 v2 로 미루는 편이 안전하다.

착수 전 답이 필요한 것 두 가지:
1. 이슈를 DB 개념에 흡수할 것인가, 병행할 것인가 (1-5)
2. 실시간 편집 중 문서에 외부 API 쓰기가 들어오면 어떻게 할 것인가 (2-3)
